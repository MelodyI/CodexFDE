# 五条命令成功后 为什么反馈仍为零

本次把当前选定源码复制到新目录，初始化Git，创建新虚拟环境并重新安装。没有复用原运行数据库。环境仍是同一台Windows主机，不是容器或另一台电脑。

## 从命令结果回到结业判断

| 实际命令 | 观察 | 可以得出的结论 |
|---|---|---|
| `python -X utf8 -m workbench.cli demo` | 退出0，演示订单已发货 | 既有演示账本可运行 |
| `python -X utf8 -m eval.harness --suite blocking` | 29项通过，退出0 | 当前参考源码的阻断检查通过 |
| `python -X utf8 -m agent.loop --max-rounds 3` | 首轮converged，Token使用0 | 起点已经通过，没有调用Codex修复 |
| `python -X utf8 -m agent.graph --max-rounds 3` | completed，轨迹写明自动演示审批 | 状态图可运行，不是独立人审 |
| `python -X utf8 -m workbench.feedback summary` | total为0，退出0 | 默认目录没有反馈，不表示演示未写入 |

这组结果不能证明现场新需求已经实现。尤其要查看Graph的具体审核来源，而不只看completed。

## 两个目录导致两个不同答案

默认demo → 临时目录运行并写演示反馈 → 命令退出清理目录。

随后默认feedback summary → 读取当前目录下的默认反馈库 → 返回0条。

两条命令没有读取同一份库。为观察连续记录，本次又使用一个全新、显式指定的隔离运行目录，依次运行：

```powershell
$l16Run = ".runtime/l16-demo-followup"
python -X utf8 -m workbench.cli demo --runtime-dir $l16Run
python -X utf8 -m workbench.cli feedback --runtime-dir $l16Run
```

请选择尚不存在、专用于演示的目录；demo会重置该演示账本，不应指向实际业务目录。本次对照结果为1条反馈。这里使用支持目录参数的workbench.cli入口，不能把参数直接照抄给不支持它的workbench.feedback模块。

## 为什么一条记录仍不是完整交付

这条记录来自脚本中的demo-day来源，任务的审核由demo-reviewer演示策略完成。它证明指定目录能够串起演示和回查，不证明真人提出意见、独立审核者接受候选，或反馈已推动下一次开发。结业仍需现场新需求、范围内修改、同候选复验和真实反馈来源。

用这组对照改进答辩方法：先指出对象和目录，再解释退出码与业务状态，最后说明人工判断从哪里来。机器报告显示成功时，仍应把实际完成的层次讲清楚。
