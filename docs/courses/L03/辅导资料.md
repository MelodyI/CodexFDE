# L03｜把模糊需求变成可验收 Spec

> 本资料只解释“为什么”。具体命令、Prompt 和提交方法见[实践操作手册](./实践操作手册.md)。

## 本讲要解决的问题

“增加库存导出功能”听起来像一个需求，其实无法直接判断完成。

它没有说明：谁使用、导出哪些列、一行代表什么、可用量怎样计算、空库存怎么办、写文件失败后能否留下半成品。不同开发者可以做出互相冲突的实现，而且都声称自己理解正确。

L03 要把这句话变成一份**可解析、可反驳、由人确认**的库存导出合同，并给工作台增加一个最小 Spec 解析器。

![从模糊需求到确认版合同](assets/lesson-overview.png)

## 1｜Spec 不是需求作文，而是判断合同

Spec 的作用不是把需求写长，而是让实施者、测试者和验收者能够回答同一组问题：

- 本次要改变什么？
- 哪些事情明确不做？
- 哪些业务规则不能破坏？
- 给定具体输入，应该观察到什么？
- 留下哪些证据后，谁可以接受交付？

因此，“支持库存导出”不是合格验收项；“在库 8、预占 3 时，导出的可用量为 5”才是可观察结果。

```text
模糊愿望 → 业务追问 → 人工作出决定 → Spec → 实现与验收
```

Codex 可以发现歧义并提出选项，但不能替业务负责人决定库存口径、行粒度和接受条件。

## 2｜先问用途，再问字段

字段不是凭空产生的。先问“谁拿这份导出作什么决定”，才能判断需要怎样的数据粒度。

例如，同一 SKU 分布在两个仓库：

| 使用目的 | 可能的行粒度 |
|---|---|
| 财务查看总库存 | 每个 SKU 汇总一行 |
| 仓库人员拣货 | 按仓库、仓位、批次分别列出 |

两种设计都可能合理，但不能同时成为同一份合同的默认答案。负责人必须选择，并把理由和来源留下。

本讲连续案例选择库存明细导出，至少要明确：

- 可用量口径；
- 八列字段及顺序；
- 仓库、仓位、批次的行粒度；
- 稳定排序；
- 空库存输出；
- CSV 特殊字符；
- 写出失败与只读性。

这些是需要确认的业务决定，不是解析器自动推断的内容。

## 3｜六部分合同分别解决什么问题

课程使用固定的六段式 Spec：

| 章节 | 回答的问题 |
|---|---|
| 来源 | 原始诉求、事实依据、决定人和确认状态是什么？ |
| 目标 | 谁使用，解决什么问题，本次交付什么？ |
| 非目标 | 哪些相邻功能本轮明确不做？ |
| 约束 | 哪些业务规则、数据边界和技术限制必须遵守？ |
| 验收用例 | 给定什么，执行什么，预期看到什么？ |
| 完成定义 | 要哪些证据、由谁接受、什么情况下不能交接？ |

### 目标与非目标必须成对出现

目标说明终点，非目标控制扩张。例如，本讲确认“库存导出合同”，不顺手加入低库存提醒、采购建议或订单导出。

### 约束与验收用例不能互相替代

约束写通用规则：

```text
可用量 = 在库量 - 预占量，结果不得为负。
导出只读，不改变库存和流水。
```

验收用例用具体数据证明规则可以被检查：

```text
给定在库 8、预占 3，执行导出后，可用量列为 5；
导出前后库存及流水保持一致。
```

### 完成定义不能写成“测试通过”

它还要说明测试覆盖范围、实际输出、剩余问题和具名接受者。自动检查只能提供证据，不能代签业务决定。

## 4｜一份可验收的库存导出合同

库存导出至少应覆盖以下路径：

| 情境 | Spec 必须给出明确预期 |
|---|---|
| 正常数量 | 在库、预占和可用量的具体例子 |
| 多仓、多仓位、多批次 | 一行代表什么，按什么顺序输出 |
| 空库存 | 只输出表头、输出空文件还是报错 |
| 特殊字符 | 中文、逗号、引号和换行如何保持可读取 |
| 写出失败 | 是否保留半成品，已有目标文件怎样处理 |
| 只读性 | 成功和失败后哪些业务状态必须不变 |

只写正常路径会让大量实现差异留到开发阶段才爆发。错误路径不是“补充测试”，而是合同的一部分。

## 5｜反例为什么比润色更有用

审查 Spec 时，不要先问“写得是否专业”，先找一句可能产生两种实现的话。

例如：

> 每个商品导出一行。

遇到同一商品分布在两个仓库时，这句话可能表示汇总一行，也可能表示每个仓库一行。一个反例立刻暴露行粒度没有定义。

有效修订应留下三层痕迹：

1. 初稿怎样写；
2. 哪个反例暴露了歧义；
3. 谁选择了哪种解释，为什么。

Codex 的审查意见是候选证据，不是业务确认。课堂角色确认也必须注明“角色练习”，不能冒充真实客户签字。

## 6｜模板复用结构，不复用业务答案

确认库存 Spec 后，可以抽取一个六段式模板。模板只保留章节和填写提示：

```markdown
## 来源
<!-- 原始诉求、事实依据、确认人、确认状态 -->

## 目标
<!-- 使用者、业务问题、本次交付 -->
```

库存公式、字段、仓位和人员不能进入通用模板。用同一模板起草“采购申请导出”时，采购状态、权限和字段都要重新确认。

复用的是提问框架，不是上一项业务的答案。

## 7｜解析器只检查结构，不判断业务真伪

工作台解析器的职责很小：

- 接受六个标题完整、顺序正确且正文非空的 Spec；
- 返回六个字段的原文；
- 对缺章、空章、重复、乱序、未知章节和未闭合代码围栏给出明确错误；
- 读取过程中不修改输入文件。

它不应该硬编码“可用量 = 在库量 - 预占量”。否则通用解析器就只能服务库存需求。

三种输入可以清楚说明边界：

| 输入 | 解析器 | 人工业务审查 |
|---|---|---|
| 六段完整、口径正确 | 通过 | 可以继续确认 |
| 缺少“非目标” | 拒绝 | 无需进入业务审查 |
| 六段完整、库存公式错误 | 通过 | 用业务反例退回 |

**结构通过不等于业务正确。** 这是本讲最重要的证据边界。

## 8｜为什么要先红后绿

如果解析器已经写完才补测试，绿灯只能说明测试与当前实现相容，不能证明测试能发现能力缺失。

有真实缺口时，应先让测试暴露缺失，再做最小实现，最后用同一测试复验：

```text
缺失能力 → 测试红灯 → 范围内 Diff → 同一测试绿灯
```

如果起点已经具备能力并全绿，就如实记录“参考能力复验”，不要破坏实现制造红灯。学生仍需解释测试覆盖什么、CLI 是否调用同一个解析器、错误输入是否返回非零退出码。

## 9｜L03 的人机分工

Codex 可以：

- 调查实现与已有规则；
- 追问缺失条件并展示冲突方案；
- 起草 Spec、模板、测试和解析器候选；
- 运行结构检查并报告实际结果。

学生必须：

- 决定使用目的、口径、范围和验收条件；
- 区分事实、假设、建议与负责人决定；
- 用反例判断歧义是否真正消除；
- 确认解析器的能力边界；
- 签署确认版或明确标记“待确认”。

本讲的学习证据不是一份漂亮文档，而是**初稿、歧义标注、修订决定和真实复验**能够互相对应。

## 一页总结

1. Spec 是判断合同，不是需求作文。
2. 先明确使用者和用途，再决定字段与行粒度。
3. 六段式结构固定，业务内容必须逐项确认。
4. 正常、空数据和失败路径都要有可观察结果。
5. 反例用来暴露歧义，Codex 建议不能代替人确认。
6. 模板复用结构，不复用库存业务答案。
7. 解析器检查结构，人审判断语义，L04 才验证产品实现。

下一讲 L04 将使用本讲确认的同一份库存 Spec，委托 Codex 完成受控实现。执行者不能临时换题，也不能用“测试绿了”替代合同验收。

## 课程合同

- **主题：**把模糊需求变成可验收 Spec
- **核心内容：**目标与非目标、正常与错误路径、边界条件、可执行验收项、最小变更原则。
- **演示结果：**把“增加导出功能”拆成结构化 `FDE_SPEC.md`。
- **课内增量：**实现 Spec 模板与最小解析器，只负责生成和校验结构，不执行编码。
- **通过标准：**Spec 至少包含目标、非目标、约束、验收用例和来源；缺失必要字段时返回明确错误。

本讲对应 CLO-2。FlowERP 新增的是**签字确认的库存导出合同**，不是已经实现的导出功能；工作台新增的是六段式 Spec Schema、模板和结构闸门。
