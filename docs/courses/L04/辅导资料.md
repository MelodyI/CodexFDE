# L04｜委托 Codex 执行一次最小变更

> 本资料只解释“为什么”。具体命令、Prompt 和提交方法见[实践操作手册](./实践操作手册.md)。

## 本讲要完成一次自举换挡

L01～L03 中，学生直接监督 Codex 建设规则、Spec 和解析能力。到 L04，需要完成一次关键换挡：

```text
学生直接监督 Codex
        ↓
补齐并验收 Workbench V0
        ↓
Workbench V0 组织人与 Codex
        ↓
首次交付 FlowERP 库存导出
```

![L04 从建设工作台到工作台交付客户产品](assets/lesson-overview.png)

本讲有两个连续成果，缺一不可：

- 可运行、经过独立验收的个人研发工作台 V0；
- 由该工作台依据 L03 确认版 Spec 交付的库存导出。

如果直接让 Codex 修改 FlowERP，就跳过了工作台自举；如果只把工作台搭出来却不交付库存导出，就没有证明工作台能够组织真实交付。

## 1｜为什么必须分成 Ticket A 和 Ticket B

### Ticket A：建设并验收工作台 V0

A 的对象是个人研发工作台。它至少要能：

- 绑定一份结构有效的 Spec；
- 创建可追查任务；
- 区分“只复验”和“调用 Codex 编码”；
- 限定工作目录、允许写集和超时；
- 保存实际调用、输出、退出码和 Diff；
- 运行最小 Eval 并生成结果摘要；
- 检查通过后停在待人工审核。

### Ticket B：由已接受的 V0 交付库存导出

B 的对象是 FlowERP。它必须引用：

- 已由非执行者接受的 A；
- L03 的同一份确认版库存导出 Spec；
- 明确的允许写集和验证命令。

只有 A 被独立接受后，B 才能启动。这样可以避免“用一个尚未证明可信的执行器，证明它自己完成了客户交付”。

## 2｜工作台 V0 的最小架构

```text
确认版 Spec
    ↓ 绑定
Task + 能力信封
    ↓ 授权
Codex 在隔离候选中执行
    ↓
实际 Diff + 命令输出 + 退出码
    ↓
最小 Eval
    ↓
review：等待具名审核者接受或打回
```

工作台不是另一个聊天窗口。它的价值在于把合同、授权、执行、证据和人工决定绑定到同一任务。

## 3｜能力信封如何限制一次执行

“请按 Spec 完成开发”仍然太宽。一次受控委托至少要固定五项边界：

| 边界 | 必须回答的问题 |
|---|---|
| 输入 | 使用哪一份、哪个版本的 Spec？ |
| 工作目录 | Codex 在哪个候选工作区执行？ |
| 写集 | 哪些文件允许修改？ |
| 时间 | 多久必须停止并报告？ |
| 检查 | 用哪些命令判断结果？ |

这五项合起来形成能力信封。执行者可以在信封内自主调查、修改和测试；遇到范围不足时应停止并申请扩大范围，而不是自行越界。

### 为什么写集要从 Spec 推导

库存导出涉及领域读取、CSV 文件输出、命令入口和测试。允许写集应包含完成这些职责所需的最小文件，而不是授权“整个项目”。

写集太小会导致合法实现无法完成；写集太大则无法判断哪些修改属于本次交付。两种情况都需要显式处理。

## 4｜执行成功不等于交付完成

一次 B 任务至少有四层结果：

| 层级 | 问题 |
|---|---|
| 进程结果 | Codex 调用是否结束，退出码是什么？ |
| 范围结果 | 实际修改是否全部落在允许写集？ |
| Eval 结果 | 合同声明的业务情境是否通过？ |
| 人工决定 | 审核者是否接受本次候选？ |

退出码 0 只回答第一层。测试通过也不能替代范围检查和人工接受。

因此，工作台的正确终态不是自动写成 `completed`，而是停在 `review`：证据已准备好，等待具名审核者作出接受或打回决定。

## 5｜怎样验证库存导出

L03 已经定义合同，L04 必须按同一份合同验证真实产品结果。

### 5.1 CSV 结构

固定八列及顺序：

```text
sku,name,site,location,lot_id,on_hand,reserved,available
```

CSV 应使用真正的 CSV 读取器验证，不能靠目测逗号数量。商品名称中的逗号、引号和换行必须能够正确还原。

### 5.2 数量与排序

至少验证：

- 东仓在库 8、预占 3，可用量 5；
- 西仓在库 12、预占 4，可用量 8；
- 每条仓库、仓位、批次明细独立输出；
- 按 `sku → site → location → lot_id` 稳定排序。

### 5.3 空库存与文件失败

空库存输出只有表头。文件写出中途失败时：

- 已存在的目标文件保持原样；
- 原本没有目标文件时，不留下半成品；
- 返回明确失败，而不是假装成功。

### 5.4 只读性

导出成功或失败后，库存数量和业务流水都必须不变。CSV 正确但库存被修改，仍然是失败交付。

## 6｜为什么需要独立复验

执行者最了解自己做了什么，也最容易沿着自己的假设检查。独立复验者应从合同出发，而不是从实现说明出发：

1. 确认使用的是 L03 同一份 Spec；
2. 查看实际 Diff，而不是摘要中的文件清单；
3. 在同一候选上重新运行检查；
4. 查看失败路径和执行后状态；
5. 给出接受、打回或证据不足的具名决定。

没有独立复验者时，任务可以停在 `review`，但不能声称已经完成验收。

## 7｜失败怎样推动工作台升级

失败分成两类：

| 失败对象 | 例子 | 下一步 |
|---|---|---|
| FlowERP 候选失败 | CSV 列错、排序错、文件保护失败 | 打回 B，在新候选上修复并复验 |
| 工作台失职 | 漏报越界、吞掉失败、状态与真实结果矛盾 | 暂停 B，先修复并重新验收 A |

这就是 FDE 的现场、交付、能力循环：产品失败不仅触发修复，也可能暴露工作台缺口；工作台升级后再回到真实产品中验证。

失败记录不能删除。新的修复任务应引用原任务和原证据，让别人能看出问题如何被发现、怎样修订、为何最终接受。

## 8｜L04 的人机分工

Codex 可以：

- 调查 V0 缺口并起草建设合同；
- 在授权范围内补齐工作台；
- 依据绑定 Spec 修改 FlowERP 候选；
- 运行检查、整理 Diff 和生成摘要；
- 根据打回意见进行有界返工。

学生和审核者必须：

- 决定能力信封和允许写集；
- 确认使用哪一份 Spec；
- 判断检查是否覆盖合同；
- 独立复验候选和失败后状态；
- 作出接受、打回或证据不足的决定。

工作台组织协同，但不取代需求负责人、执行授权者和最终审核者。

## 一页总结

1. L04 必须先完成 A，再由已接受的 V0 执行 B。
2. 工作台把 Spec、授权、执行、证据和人审绑定到同一任务。
3. 能力信封固定输入、工作目录、写集、时间和检查。
4. 退出码 0、测试绿灯和人工接受是不同结论。
5. 库存导出要检查八列、数量、排序、特殊字符、文件失败和只读性。
6. 产品失败返工 B；工作台失职先返工 A。

下一讲 L05 将面对新的问题：一个只在正确实现上通过的检查，是否真的能识别错误？届时会对重复入库先制造可信红灯，再冻结 Eval 和修复实现。

## 课程合同

- **主题：**委托 Codex 执行一次最小变更
- **核心内容：**非交互执行、工作目录、权限边界、结果采集与人工确认点。
- **演示结果：**读取第 03 讲 Spec，委托 Codex 完成一个小型代码变更并运行测试。
- **课内增量：**完成执行入口和结果摘要；仓库文件由 Codex 在授权工作区直接处理，不额外包装为文件读写 MCP。
- **通过标准：**变更能够运行；基础测试通过；摘要包含修改文件、验证命令和剩余风险；密钥和环境文件未提交。

本讲对应 CLO-2。FlowERP 新增库存导出；工作台完成 V0，并从“由学生直接监督 Codex 搭台”切换为“由工作台组织人与 Codex 协同交付”。
