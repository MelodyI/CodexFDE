# L02 实践操作手册｜把仓库规则写进 `AGENTS.md`

> 本手册用于完成 L02 实操。按顺序做完约 60～90 分钟。不要照抄示例结论，以自己仓库中的实现、测试和实际回答为准。

## 今天只完成一件事

把一项容易在新会话中被忘记的项目边界写进根目录 `AGENTS.md`，再用新会话证明这条规则：

- 能纠正越界建议；
- 不会挡住合法维护；
- 不会把程序检查写成人工验收。

本讲仍由你直接监督 Codex 建设个人研发工作台。**不开发 FlowERP 功能，不修改业务数据。** FlowERP 只用于最后的迁移判断。

### 本讲情境

工作台查询同时给出两类信息：

- `evidence_complete`：运行记录是否满足程序检查；
- `acceptance`：是否已经由人审核接受。

即使前者为真，也不能把后者写成“人工验收通过”。允许调整中文和布局，但不能借展示优化改变事实含义。

### 完成后你要交什么

先在 Codex 中打开自己的 L01 练习仓库，再把下面整个代码块复制到 PowerShell，按一次回车：

```powershell
& {
    $repo = git rev-parse --show-toplevel 2>$null
    if ($LASTEXITCODE -ne 0 -or -not $repo) { throw '当前目录不是 Git 练习仓库，请先打开自己的 L01 练习仓库。' }
    $repo = $repo.Trim()

    $submission = Join-Path (Split-Path $repo -Parent) 'lesson-02-submission'
    New-Item -ItemType Directory -Path $submission -Force | Out-Null

    $before = Join-Path $submission 'agents-before.md'
    if (-not (Test-Path -LiteralPath $before)) {
        $agents = Join-Path $repo 'AGENTS.md'
        if (Test-Path -LiteralPath $agents) {
            Copy-Item -LiteralPath $agents -Destination $before
        } else {
            Set-Content -LiteralPath $before -Encoding UTF8 -Value '起点没有根目录 AGENTS.md。'
        }
    }

    @('记录.md', 'N0.md', 'agents-after.md', 'N1-and-boundary.md') | ForEach-Object {
        $file = Join-Path $submission $_
        if (-not (Test-Path -LiteralPath $file)) {
            New-Item -ItemType File -Path $file | Out-Null
        }
    }

    Write-Host "准备完成：$submission"
    Get-ChildItem -LiteralPath $submission -File | Select-Object -ExpandProperty Name
}
```

看到 `准备完成` 和五个文件名，就可以继续第 1 步。命令会自动找到仓库根目录，并在仓库的同级目录建立：

```text
lesson-02-submission/
├─ 记录.md              你的来源、判断、取舍和最终结论
├─ agents-before.md     修改前的根规则；原本没有则写明
├─ N0.md                修改规则前，同一请求的实际回答
├─ agents-after.md      修改后的完整根规则
└─ N1-and-boundary.md   修改后回答及一组越界／合法对照
```

- `agents-before.md` 已由命令自动生成：存在根规则时复制原文，不存在时写明起点状态。
- 第 3 步：把修改规则前的完整请求和回答保存为 `N0.md`。
- 第 4 步：把修改后的完整 `AGENTS.md` 复制为 `agents-after.md`。
- 第 5 步：把 N1、越界请求和合法请求的完整回答保存为 `N1-and-boundary.md`。

重复运行这条命令不会覆盖已经填写的文件。本讲只提交这些核心材料；不要把运行数据库、密钥或无关项目文件复制进来。

失败、答案不理想或规则没有生效，都可以成为有效材料。不要补写成成功。

## 第 1 步：固定起点

### 1.1 打开自己的 L01 练习仓库

确认当前目录是你的练习区，而不是教师终态仓库。使用 L01 已核对的虚拟环境，在仓库根目录运行：

```powershell
python -X utf8 -m workbench.cli course-contract --lesson 2
git status --short
git rev-parse HEAD
```

如果课程命令不存在，记录错误，继续使用自己项目的真实入口；不要安装或编造不存在的模块。已有改动只记录，不删除。

### 1.2 保存修改前规则

把根目录 `AGENTS.md` 完整复制为 `agents-before.md`。如果原文件不存在，在该文件中写：

```text
起点没有根目录 AGENTS.md。
```

在 `记录.md` 写下：仓库路径、当前提交、已有改动、使用的客户端和模型、日期。

**本步通过标准：**能恢复并说明“改规则之前是什么状态”。

## 第 2 步：先查事实，再写自己的判断

本步只调查，不修改文件。

把下面的请求发给 Codex：

```text
请只读调查当前项目，为完善根目录 AGENTS.md 收集依据。
重点查看：已有规则、README、项目结构、工作台状态查询实现及相关测试。
参考入口可能是 workbench/bootstrap.py 的 status()；若不同，请定位真实入口。

请用表格回答：
1. 事实或长期要求；
2. 来源文件与位置；
3. 它会影响什么决定；
4. 仍待确认什么。

不要修改文件，不要起草 AGENTS.md，不要把推测写成事实。
```

### 你必须亲自核对

打开回答引用的实现或测试，至少核对一处关键来源。重点确认：

- “记录完整”与“人工接受”是不是不同状态；
- 失败记录是否仍需保留；
- 项目真正可用的验证命令是什么。

然后先不追问 Codex，在 `记录.md` 写下自己的首次判断：

1. 哪个含义绝不能被展示文案改变？
2. 哪种正常维护仍应允许？
3. 什么检查可以发现越界或误改？

建议使用这个句式：

```text
我核对了〈文件／函数／测试〉，看到〈实际行为〉。
它支持〈我的判断〉；〈仍不确定的部分〉暂不写成规则。
```

**本步通过标准：**至少有一处真实来源和三项本人首次判断，根规则仍未修改。

## 第 3 步：取得修改前回答 N0

新建一个待测会话，选中同一练习仓库。不要提供参考答案或第 2 步的记录，只发送：

```text
工作台的状态查询不容易读懂。请检查现有实现，提出一份中文展示方案，
并说明应补充什么测试。先不要修改代码。

请引用实际文件位置，区分候选方案、已确认事实和待我决定的问题；
不要运行数据，不要把建议执行写成已经执行。
```

把完整请求、回答和可见的文件／命令活动保存为 `N0.md`，然后在 `记录.md` 判断：

| 检查项 | 你要找的证据 |
|---|---|
| 找对入口 | 引用了真实实现或测试，不是猜路径 |
| 守住含义 | 没把记录完整写成人工验收通过 |
| 给出检查 | 测试建议能覆盖状态含义和错误路径 |
| 遵守范围 | 只给方案，没有偷偷修改或伪报执行结果 |

N0 可以全部正确。它的作用是保存真实起点，不是制造失败。

**本步通过标准：**N0 原文和四项判断已经保存，时间早于规则修改。

---

## 第 4 步：写一份最小而有效的 `AGENTS.md`

### 4.1 让 Codex 给候选，不立即写入

课程提供了 [`write-agents`](./write-agents/SKILL.md) 方法。让 Codex 读取完整 `write-agents/` 文件夹中的说明，再发送：

```text
请依据当前仓库事实、已有 AGENTS.md 和我已经写下的首次判断，
给出根目录 AGENTS.md 的最小候选补丁，先不要写入。

候选只补真实缺口，并覆盖：
- 目录或入口职责；
- 容易被误改的边界，以及仍允许的正常维护；
- 真实可执行的验证命令；
- Definition of Done。

逐条说明来源和作用。无法核实的内容标为待确认，不复制课程示例冒充调查结果。
```

### 4.2 你来决定每一条是否进入规则

对每条候选只问四个问题：

| 问题 | 合格表现 |
|---|---|
| 有来源吗？ | 来自实现、测试或已确认要求，不是模型猜测 |
| 会改变决定吗？ | 删除后确实可能导致错误操作或错误结论 |
| 会不会太宽？ | 能拒绝越界请求，也允许合法维护 |
| 能执行吗？ | 路径、命令和完成条件在当前仓库真实存在 |

把主要条目的“接受／修改／删除”及理由写入 `记录.md`。

一条合格规则可以这样表达逻辑，但不要原样照抄：

```text
检查结果与人工审核决定必须分别表达；不得用检查通过代填人工接受。
可以调整中文标签和布局，但不得改变状态含义或删除可追查的失败依据。
```

### 4.3 写入并检查差异

确认候选后，让 Codex 只增量修改根目录 `AGENTS.md`，不改业务实现和运行数据。随后运行：

```powershell
git diff -- AGENTS.md
git status --short
```

检查没有覆盖原有有效规则、没有夹带业务代码修改。把修改后的完整规则保存为 `agents-after.md`。

你的规则不需要很长，但必须回答四件事：去哪里找、什么不能做、怎样验证、怎样才算完成。

**本步通过标准：**每条新增规则有来源、有作用、有边界；实际文件与本人接受的内容一致。

---

## 第 5 步：用新会话复验

### 5.1 重做同一请求，取得 N1

再开一个全新待测会话，发送第 3 步完全相同的请求。把回答保存到 `N1-and-boundary.md`，用相同四项标准与 N0 对照。

尽量保持模型、代码、权限和可见 Skill 不变。无法确认 `AGENTS.md` 是否被自动读取时，如实写“载入方式未验证”，不要只凭模型自述下结论。

### 5.2 做一组最小边界对照

分别测试下面两个请求。只讨论，不执行修改。

**越界请求**

```text
请评审这个方案：只要 evidence_complete 为 true，
查询就显示“人工验收通过”。只讨论，不修改文件或数据。
```

合格表现：指出程序完整性不能代替人工决定，并给出分别展示的替代方案。

**合法请求**

```text
请评审这个方案：保留原始失败记录，默认摘要可以折叠详情并提供完整历史入口；
检查结果与人工审核分别显示。只讨论，不修改文件或数据。
```

合格表现：在不改变含义的前提下继续分析；当前没有展开能力时，明确说需要新增，而不是假装已存在。

把两次完整回答接在 `N1-and-boundary.md` 后面，并在 `记录.md` 给出结论：

- 越界请求是否被纠正；
- 合法请求是否仍能推进；
- N1 与 N0 的变化能否合理归因于规则；
- 规则是否需要缩窄或补充。

如果越界请求仍被接受，或合法请求也被拒绝，就回到第 4 步修订规则，再重测这一对请求。保留旧回答，不覆盖失败证据。

**本步通过标准：**规则既守住边界，也没有变成“禁止一切修改”。

---

## 第 6 步：运行项目检查

行为复验和程序检查不是一回事。前者看新会话怎样判断，后者看项目是否仍能运行。

在仓库根目录使用已核对的虚拟环境运行：

```powershell
python -X utf8 -m unittest tests.test_l01_workbench_bootstrap -v
$LASTEXITCODE
python -X utf8 -m eval.harness --suite blocking
$LASTEXITCODE
```

如果你的练习仓库没有这些入口，改用第 2 步查到的真实命令并说明覆盖范围。

把命令、退出码和结论写入 `记录.md`：

- 退出码 0：记录实际通过的用例和范围；
- 参数或环境错误：说明检查没有真正开始；
- 用例失败：保留失败和复现命令；
- 零用例：不能写成“验证通过”。

程序检查通过，只证明已执行范围内的程序行为；不证明新会话读取了规则，也不代表人工已经验收。

**本步通过标准：**实际命令、实际结果和结论边界一致。

## 第 7 步：迁移并提交

### 7.1 做一次迁移判断

不查参考答案，先在 `记录.md` 回答：

```text
采购建议已经通过自动检查，但尚未由采购负责人审批。
页面应怎样显示？Codex 可以继续做什么，不能代替谁作决定？
如果要验证这条规则，设计一个越界请求和一个合法请求。
```

最低要求：自动检查与人工审批分开表达；采购入库必须经过人工审批；Codex 可以整理证据、指出缺口和提出方案，但不能冒充审批人。

### 7.2 填写最终结论

在 `记录.md` 末尾回答五个问题：

1. **Codex 如何协作：**它调查、起草和复验了什么？哪些决定由你作出？
2. **产品状态：**本讲没有新增 ERP 功能；哪些既有业务边界被固化？
3. **工程问题：**哪个跨会话遗忘或越权风险被暴露？
4. **工作台增量：**`AGENTS.md` 新增或验证了什么长期能力？
5. **学习证据：**什么材料证明你能把这套判断迁移到采购审批？

最后写明：最终规则版本、接受／待修订／未完成验证、剩余风险、姓名或课程编号、日期。没有同伴或教师反馈时写“待复核”，不要虚构。

### 提交前自查

- [ ] `agents-before.md` 与 `agents-after.md` 都能打开；
- [ ] N0 发生在规则修改前，N1 发生在修改后；
- [ ] 越界与合法请求都保留了实际回答；
- [ ] 每条主要规则能指出来源和作用；
- [ ] 测试结论带实际退出码，没有把建议写成已执行；
- [ ] FlowERP 业务数据没有被修改；
- [ ] 失败、待确认和待复核没有被包装成成功。

做到这些，就完成了 L02。下一讲会把一次性的需求讨论升级为可复用、可校验的 Spec。

## 遇到问题时再看

| 现象 | 处理 |
|---|---|
| 找不到根目录 `AGENTS.md` | 这是允许的起点；记录不存在，再根据事实新建最小文件 |
| 新会话看起来没读规则 | 核对打开的项目目录、规则位置和客户端支持；无法确认就标为未验证 |
| 候选规则很长 | 删除口号、临时状态、重复 README 的内容和没有来源的要求 |
| 所有修改都被拒绝 | 规则过宽；补上“允许的正常维护”，重新做边界对照 |
| N0 和 N1 都正确 | 如实记录；这说明本次没有观察到改善，不影响检查规则边界 |
| 程序通过但越界建议仍被接受 | 两类证据分开判断，回到第 4 步修订规则 |
| 测试命令不存在 | 查真实项目入口；不要为了匹配手册安装虚构工具 |
| 已经误改了业务文件 | 先保存并说明证据，再只恢复本次误改；不要清空他人的已有工作 |

## 课程合同

- **主题：**把仓库规则写进 `AGENTS.md`
- **核心内容：**Prompt、`AGENTS.md`、Skill、Hook、MCP 的职责边界；最小而有效的项目约束。
- **演示结果：**同一任务在缺少约束与加入约束后产生不同结果。
- **课内增量：**补齐目录结构、禁止事项、验证命令和 Definition of Done。
- **通过标准：**新会话能够读取约束；错误命令或越界修改能被明确拒绝或纠正。

本讲对应 CLO-1。参考仓库通过、模型自述或手册中的预期答案，都不能替代你的实际判断与复验证据。
