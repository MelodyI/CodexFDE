# L02｜把仓库规则写进 `AGENTS.md`

> 这份资料只解释“为什么这样做”。具体命令、Prompt 和提交方法见[实践操作手册](./实践操作手册.md)。

## 本讲要解决的问题

上一次会话里，Codex 已经知道项目边界；换一个新会话，它还会遵守吗？

L02 的答案不是“写一个更长的 Prompt”，而是把**跨任务仍然成立、会影响工程决定、能够被复验**的约定写进仓库根目录 `AGENTS.md`。

本讲的案例很小：工作台查询同时显示“运行记录是否完整”和“是否经过人工审核”。小问题背后有一个重要边界：

> 程序观察到的事实，不能冒充人的决定。

因此，`evidence_complete = true` 可以显示为“运行记录完整”，但不能被翻译成“人工验收通过”。中文和布局可以调整，状态含义不能被偷换。学完工作台案例后，同一判断会迁到采购：申请存在、检查通过、负责人批准是三件不同的事；本讲固化这类边界，不改 FlowERP 业务账。

## 1｜为什么聊天里的提醒不够

一次会话中的提醒，只解决眼前任务。新会话没有那段讨论时，同一种误判可能再次出现：

```text
运行记录完整
        ↓ 错误合并
人工已经验收
```

这不是翻译风格问题，而是责任边界被改变了。

如果一个约定同时满足下面三个条件，它就值得成为仓库规则：

| 判断 | 要问的问题 | 本讲案例 |
|---|---|---|
| 长期成立 | 换一个任务或会话，它还成立吗？ | 自动检查不能代替人工接受 |
| 影响决定 | 不知道它，Codex 可能做错什么？ | 把待审核显示成已通过 |
| 可以复验 | 能设计错误与合法请求检查它吗？ | 拒绝冒充人审，同时允许中文优化 |

“今天库存为 8”“这次先改首页颜色”属于当前状态或单次任务，不应写成长期规则。

## 2｜五种机制分别解决什么问题

本讲同时出现 Prompt、`AGENTS.md`、Skill、Hook 和 MCP。它们不是五种写法，而是解决不同问题的机制。

| 机制 | 负责什么 | 本讲怎样使用 |
|---|---|---|
| Prompt | 说明这一次要做什么 | 请检查中文展示，先给方案，不改代码 |
| `AGENTS.md` | 保存项目长期约定 | 自动结果与人工决定必须分开表达 |
| Skill | 复用一套工作方法和配套资源 | 按“调查—筛选—起草—审查”写规则 |
| Hook | 在特定事件发生时触发检查 | 后续可在写入或提交时自动运行检查 |
| MCP | 连接仓库外的工具或已授权资料 | 需要外部需求、工单或文档时再使用 |

本讲只要求真正用好前两项，并体验一次写规则的 Skill。不要为了“覆盖概念”安装 Hook 或 MCP。

官方 OpenAI 文档说明，Codex 会从项目根目录沿当前工作目录查找并组合 `AGENTS.md` 指令；更接近当前目录的指令后出现，因此可以细化上层规则。Skill 则适合封装可重复的方法、模板与参考资源。具体机制会更新，开课前应重新核对官方文档。

## 3｜什么应该写进 `AGENTS.md`

一份最小而有效的项目规则，应回答四个工程问题。

### 3.1 去哪里找

告诉下一位执行者关键目录或入口分别负责什么，而不是罗列整个仓库。

```text
workbench/：研发任务、运行记录及其查询。
eval/：统一质量检查入口。
tests/：已有行为和错误路径的自动检查。
```

路径必须来自当前仓库调查。不存在的目录和旧入口不能因为“示例里有”就照抄。

### 3.2 什么不能做

有效边界必须同时写清禁止事项和合法路径。

```text
检查结果与人工审核决定必须分别表达，不得用检查通过代填人工接受。
允许调整中文标签和布局，但不得改变状态含义。
```

只有“不得改变状态”太宽，可能连正常翻译也挡住；只有“保证状态正确”太空，不足以指导决定。

### 3.3 怎样验证

验证命令必须在当前仓库真实存在，并说明它覆盖什么。

```text
python -X utf8 -m eval.harness --suite blocking
```

命令写进规则不等于已经运行。参数错误、环境错误和零用例也不能写成“检查通过”。

### 3.4 什么才算完成

Definition of Done 规定交接时必须留下什么，而不是写一句“保证高质量”。例如：

- 报告实际修改的文件和范围；
- 区分已执行检查与建议检查；
- 报告真实结果、退出码和未验证事项；
- 自动检查不代替具名人工接受。

目录职责帮助定位，边界保护含义，验证命令检查行为，完成条件约束交接。四部分共同服务一次可追查的交付。

## 4｜规则不是禁令清单，而是决策边界

判断一条规则是否写得好，最有效的方法不是看它是否严厉，而是准备一对只差关键条件的请求。

| 请求 | 应有反应 |
|---|---|
| “记录完整就显示人工验收通过” | 纠正含义，并给出合法替代 |
| “分别显示记录完整和人工审核，只优化中文” | 继续分析或实施已授权维护 |

如果两个请求都被接受，规则没有守住边界；如果两个都被拒绝，规则过宽。

规则候选可以用“删、改、留”审查：

- **删：**口号、临时状态、重复 README 的内容、没有来源的要求；
- **改：**把宽泛禁令改成具体触发条件，并补上允许的合法路径；
- **留：**容易猜错的业务语义、真实验证入口、失败处理和交接要求。

规则越长，维护成本越高，也越容易掩盖真正重要的边界。长度不是完整性的证明。

## 5｜怎样证明规则真的有用

保存了 `AGENTS.md`，还不能直接得出“规则已生效”。本讲需要区分三类证据。

| 证据 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 来源与规则差异 | 规则依据什么事实、实际改了什么 | 新会话一定按它判断 |
| N0、N1 与边界回答 | 这几次会话怎样处理具体请求 | 所有任务都有效，变化只由规则造成 |
| 命令、输出和退出码 | 本次程序检查实际得到什么结果 | 人工已经接受，未覆盖部分也正确 |

![规则内容、会话行为和程序结果是三类证据](./图解/复验证据.png)

### 为什么要有 N0 和 N1

N0 是修改规则前的真实回答，N1 是修改后用相同请求得到的回答。它们用于观察变化，不是为了制造“前错后对”的表演。

- N0 已经正确：如实记录，本例没有观察到改善；
- N1 更好：说明本次结果与规则方向一致，但仍要记录模型、代码和上下文差异；
- N1 仍然错误：回到规则来源与措辞继续修订；
- 合法请求也被拒绝：说明规则过宽，需要收窄。

模型说“我读取了规则”，不能单独证明发现机制成功；测试绿灯也不能证明回答遵守了规则。结论必须与证据类型一致。

## 6｜人和 Codex 怎样分工

Codex 可以：

- 查找实现、测试和已有规则；
- 提出候选条目及其来源；
- 修改已授权的文件；
- 运行检查并报告真实结果；
- 用新请求协助复验规则边界。

学生必须：

- 判断哪些事实值得升级为长期约定；
- 决定候选规则接受、修改还是删除；
- 识别自动结果与人工责任的边界；
- 独立解释失败、限制和迁移结论；
- 作出最终接受、退回或证据不足的决定。

这就是本讲的学习证据：不是“AI 帮我生成了一个文件”，而是你能说明每条主要规则从哪里来、改变什么决定、怎样被反例检验。

## 7｜迁移到采购审批

把工作台案例换成 FlowERP：

> 采购申请已经建立，自动检查也通过了。能否先把库存加上，审批明天再补？

不能。申请存在、检查通过和采购负责人批准，是三件不同的事。课程业务规则要求采购补货经过人工审批后才能入库。

合法路径不是“什么都不做”，而是：

1. 保留申请与自动检查结果；
2. 明确显示“等待人工审批”；
3. 由具名负责人完成审批；
4. 审批后再执行入库，并保留结果与失败证据。

这里迁移的是同一种判断方法：**区分事实与决定，拒绝越权，同时保留合法推进路径。** 工作台字段不能直接套到采购领域；仍需查阅采购服务、状态机和测试。

## 一页总结

1. Prompt 管一次任务，`AGENTS.md` 管跨任务仍成立的项目约定。
2. 只有长期成立、影响决定、能够复验的内容才值得写进根规则。
3. 最小规则回答四件事：去哪里找、什么不能做、怎样验证、何时完成。
4. 好规则既拒绝越界请求，也允许合法维护。
5. 规则差异、会话行为和程序结果是三类证据，不能互相冒充。
6. Codex 负责调查、起草和执行；学生负责来源判断、边界取舍和最终接受。

下一讲 L03 会把“这一次到底要交付什么”写成可验收 Spec。`AGENTS.md` 保存长期边界，Spec 规定单次交付，两者不能互相替代。

## 课程合同

- **主题：**把仓库规则写进 `AGENTS.md`
