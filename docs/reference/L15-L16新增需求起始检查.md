# L15 / L16：新需求的起始失败应来自哪里

先判断，再运行：如果新增需求的检查已经通过，只是旧功能出了错，这能证明本次实现了新需求吗？

本讲区分两组检查：

- 既有合同：此前已经交付的功能，本轮仍须正常。
- 新增验收：对应本次反馈或评审抽取的新需求，应能暴露当前缺少的能力。

| 起始结果 | 能否开始本次新需求执行 | 下一步 |
|---|---|---|
| 既有通过，新增失败 | 可以进入受控执行 | 实现本次范围并独立复验 |
| 既有失败，新增通过 | 不可以 | 先处理旧缺陷，重新确认需求是否尚未实现 |
| 既有和新增都失败 | 不可以 | 将旧缺陷与新需求分开，重新准备稳定起点 |
| 两组都通过 | 不可以 | 核对是否拿了参考终态，或新增断言没有检查实际缺口 |

工作台同时核对用例身份、逐项结果、汇总和退出码。缺少用例、未知用例导致的无效报告，或者只有一行“失败”自述，都不能作为起始证据。未满足条件时，任务保留失败原因，不启动 Codex。

命令入口仍由 `course-submit --lesson 15/16 --eval-case ... --session-baseline-ref ... --requirement-spec 本次需求.md --execute-code` 明确声明新增用例和起始版本；填写实际值，不复制省略号执行。本次需求文件必须包含来源、目标、非目标、约束、验收用例、完成定义，且验收段明确列出新增用例名。网页版在 L15 / L16 的补充条件中填写同样的用例与版本；从已决定事项进入时，工作台直接用已保存需求生成合同，否则需粘贴具体 Spec。通用课程说明不能替代本次需求。

通过这一道检查，只能证明报告中的失败落在新增用例组。把旧用例换名、写一个永远失败的断言，也可能呈现这种结果，因此教师或同伴必须检查：断言是否具体对应本次 Spec，错误来自产品行为还是环境故障，正常与失败路径是否都覆盖。

课堂反证：分别构造表中四种起点，先写出工作台应采取的动作，再实际验证。提交首次预测、真实逐项结果、停止或执行记录，以及修订后的合同。迁移到第二个需求时重新推导断言，不照抄用例名。

实现后仍需范围内 Diff、同一组用例的独立通过、ERP 结果对账和具名验收。起始条件通过不等于学生完成本讲，也不等于新需求已经交付。
